# Changelog

## Unreleased

- **A saved drawing stays saved.** After *save* (or Ctrl+S) in the editor, the next thing that changed no element — a move of the pointer over the canvas, a tool picked, a click on nothing — marked the drawing as unsaved again: *save* lit up, and leaving the editor asked whether to lose changes that were on the disk. The editor measured a change from the scene as it was when it opened; it now measures from the scene last saved. A stroke drawn while a save is on its way is still a change.

**Everything since 0.7.0**, by the work it came from:

### The page: easier to read, in two languages, in a look of its own

- **The heads of a review are a list to search.** The branch bar drew every branch as a box in a row, and a repository with a hundred branches was a wall of them. The heads are now a list under *branches ▾*: a row a branch, with whether it is a remote one or the one checked out, and the day and the subject of its last commit; typing cuts the list by the words of a branch's name or of that subject, Enter ticks the first one found, Escape clears. The ticked heads stand in the bar as chips, so what is reviewed or compared is in sight with the list closed, and a press on a chip unticks it. The base is picked among the local branches and the remote ones, each under its heading. A branch made after the page was opened is in the list at the next review.
- **The branches are read with one question to git.** `GET /api/branches` asked git once per branch whether it was a local one — 3.7 seconds for a hundred branches on Windows, with the server answering nothing else meanwhile, so a tap on a shape just after the page opened waited that long for its code. One `for-each-ref` now says it all (0.15 seconds for the same repository). A remote's own `HEAD`, which git shortens to the remote's name, is no longer listed as a branch called `origin`.
- **The Code tab comes at the press and says what it reads.** A tap on a shape brought the Markdown tab to the front when the shape's page landed and then the Code tab when its file did: two jumps, a moment apart on a big repository, after a wait in which nothing moved. The tab the pick is read on now comes to the front at once — the Code tab for a shape of a file, the Markdown tab for one of none — with a line that names the file being read, the code before it dimmed in its place; the page and the file are read side by side instead of one after the other. That line stays at the top while the code scrolls. A shape of no single file (a layer, a directory) says so on the Code tab instead of leaving it blank. The strip of a shape's neighbours keeps to two rows and scrolls past them: a shape with twenty neighbours no longer pushes the code a hand's breadth down. A page that lands after a newer pick is dropped, a line's page as a shape's.
- **Code in the colours of its language.** The Code tab, the code in the centre and the code blocks of a page show keywords, strings, comments, numbers and names in colour, in the light and the dark page: TypeScript, JavaScript, Python, Rust, PHP, Go, Java, C#, Kotlin, Ruby, C and C++, JSON, YAML, TOML, HTML and XML, CSS and SCSS, shell, SQL, Markdown, Dockerfile, diff. highlight.js reads the text (its core and those languages, bundled into the page: a dev dependency, as the editor is); a file of another language, or longer than 400 000 characters, stays plain. What is copied is the file's own text.
- **The page says it is waiting.** A thin bar runs under the header while the server is asked for something and has not answered within a blink — a picture, a page, a file, the branches, the settings. The settings window opens at the press and fills when the answer lands; it used to open a second later, when the server had looked for every agent's program.
- **Hints.** What a button, a tab or a mark is for is said in a bubble beside it, a moment after the pointer rests on it — at once on the next thing, when a hint is already showing — and for the keyboard's focus too. It replaces the browser's own tooltip of the same text, which came a second later, small and in the system's look. The tabs Markdown, Code and Coverage, the base field, *run*, *stop* and the other controls that had no hint have one. The violet dot beside a file in the tree and the lists says what it is where it stands: *this file is in the picture on the canvas now*. An entry of the views list is hinted with its title whole (the list cuts a long one) and its key.
- **Two languages: English and Ukrainian.** The settings window has a *Language*; the choice is kept with the user's settings (`"language": "uk"` in `~/.archdiff/settings.json`), so it holds for every repository, and the server serves the page in it (`<html lang>`), so the page knows it before it draws a word. The page's own words are translated — the buttons, the hints, the notes, the answers of the chat's commands and their help, the legend, the editor's own interface — and what archdiff writes about the code is not: a picture's page, the Mermaid, the names on the canvas and the titles of the views stay as the command line prints them. A text is named by its English where it is said (`t("fit")`, `web/src/i18n.ts`), and its translation is in a table beside (`i18n-uk.ts` and its parts); a text added without one shows in English, and a test holds the table to every text the modules say.
- **A look of its own.** One set of tokens for the colours, the corners, the shadows and the focus ring, in the light and the dark page, and one look for every control drawn from them: buttons, fields, lists, the menus' own buttons. What a part of the page is there to do — *review*, *compare*, *ask*, *run* — is a filled button. The views and the tree are two halves of one switch; the tabs are names on a line with the one in front underlined, and *copy* and *raw* at the line's end; the menus, the context menu and the settings window float with a shadow and rounder corners; the page's name has a mark. The scroll bars are thin and in the page's colours.
- **The header never loses a control.** In a window too narrow for the header's row, the controls at its end were cut off at the window's edge (*export* and the details' switch at 1100 pixels). The header now takes a second row; the repository's path and the numbers give way first, and are left out in a narrow window instead of showing a sliver.
- The settings open from a ⚙ in the header as well as from the Chat tab; the picture's options, which wore the gear, are *options ▾* like the other menus.
- The browser's tab is named for the repository (`<folder> — archdiff`): several pages open are told apart.
- A command of the Chat tab that picks a shape of a file (`/select src/x.ts`) leaves the Chat tab in front, as one that picks a layer did; the Code tab is filled behind it and scrolls to the place when it is opened.
- The note of the Chat tab's agent row (no agent found, where one is placed) takes a line of its own: a long one squeezed the picker and the settings' button into a column of letters.

**For whoever scripts the page:** an entry of the views list is found by `data-view` (its key); its `title` is its hint now.

### A release publishes itself

- A tag `v<version>` pushed to GitHub runs `.github/workflows/publish.yml`: the checks of CI on the tagged commit, then the package packed, tried as its user would get it (`archdiff --version`, a picture of this repository) and published to npm by trusted publishing — no token in the repository, no one-time code typed by hand, and the package carries the proof of where it was built. The workflow refuses a tag that is not the version of `package.json`, a tag on a commit that is not on master, and a version npm already has. npm is told once, on the package's settings page, to trust the workflow: `docs/publishing.md` says how, what a failed run means, and the way by hand, which stays for when the workflow cannot.

The architecture asked by the agent, not pasted into its prompt.

- `archdiff mcp [dir]` is an MCP server on stdin and stdout: a coding agent that speaks the Model Context Protocol (Claude Code, Codex, OpenCode) asks the analysis while it works, where until now it got pictures in its prompt. Six tools, each answered from the code as it is at the call — the analysis is read again, the fact cache keeps that fast — so the agent's own edits are in its next answer, and none changes the code, the contract or a drawing. `views` is the list `archdiff views` prints (`kind` keeps one kind, `changed` the views of the changed files); `diagram` is a view by its key as Markdown with Mermaid, with every option of the picture by the name the API's query gives it (the one table of options has a fourth reader, and the tool's schema is written from it); `check` is what `archdiff check` reports; `review` is the architectural diff of the working tree, or a head, against a base.
- `may_import` asks the contract about one import before it is written: each end a module's path (a file still to be written is placed by its path, as archdiff.json would place it) or a layer's name. The answer is *Allowed* (one layer, or an arrow of the contract across the two, which it names), *Not allowed* (the layers the importer may use, and that an import of types only is never a violation) or *Not judged* (a layer the contract does not name; no contract) — by the rule `check` holds the code to, so the two cannot disagree.
- `impact` answers what a change reaches, as `archdiff impact` reports it and from the same computation: the risk with the parts of its score; for a module, the modules that import it or call into it; for a function or a class, its callers (a class's: of its members too) — breadth-first to a depth (3 unless said), every dependent once at its shortest distance, with what it reaches the subject through and the file and line of that import or call, and the count of what lies further. The tests that reach the subject are named at any distance (a call in a test's own body counts), and the test files that only import a declaration's module apart: the tests to run after the change. A type, which nothing calls, is answered by its module, the imports of types alone counted.
- The protocol is written by hand and the package keeps its two runtime dependencies: JSON-RPC 2.0, one message per line; `initialize` (the revisions 2024-11-05 to 2025-11-25: the one asked for when the server speaks it, else the newest), `ping`, `tools/list` and `tools/call`; a batch is answered by one array, a request the client cancelled is not answered, the requests of one turn are answered as they finish, and stdout carries nothing but the protocol's messages. A wrong call — a view that does not exist, a subject the code lacks, an option that is no number, a ref git does not know, an argument the tool does not have — is a JSON-RPC error (-32602) carrying the message the CLI gives for the same mistake; a tool that ran and failed (a review outside git) is a result marked `isError` with the reason. No HTTP transport. A client of the 2026-07-28 revision, which has no handshake, is told its `server/discover` probe is not a method and falls back to `initialize`, as that revision prescribes.
- The README shows how to register the server with Claude Code, Codex and OpenCode.

The architectural diff on the pull request itself.

- The GitHub Action (`action.yml`) keeps one comment on the pull request, rewritten on every push and found again by its hidden first line: the review of the head against where it left the base — the counts, the dependencies between layers that appeared and went, the Mermaid picture, every change by kind folded below — under the verdict of `archdiff check` against ARCHITECTURE.md with its violations. The same goes to the job summary. A pull request that changed no module, function, import or call gets one line saying so instead of an empty picture.
- GitHub takes no comment over 65 536 characters, and the action sent the review whole, so the review of a big change could not be posted. Past the limit the picture stays and the lists are cut, each to the same number of its first items, with a count of what was left out; then the violations; a picture longer than the limit by itself gives way to a line. The job summary has them all.
- **Incompatible:** the action's input `fail-on-layer-coupling` is gone. `fail-on-check` (default true) fails the job when `archdiff check` finds an import between layers that ARCHITECTURE.md does not allow — in the whole code at the head, not only in the change. The old input failed the job when `review` exited 1, which without a contract is any new dependency between layers; such a dependency is still named in the comment under ⚠, and fails the job only when a contract forbids it. A comment the old action left on a pull request began with the review's own `<!-- archdiff:generated` line: the new marker does not find it, so it stays as it was beside the new one.
- The action's new input `working-directory` runs archdiff in one package of the repository. The review is measured from the merge-base whatever the job checked out (the pull request's merge commit or its head); the base ref is looked for as a branch of `origin` too; a clone without the base stops the job naming `fetch-depth: 0`, as does a Node older than 22.18 naming `actions/setup-node`. A comment that cannot be posted (a fork's read-only token, a job without `pull-requests: write`) is a warning and no failed job. The cache keeps the files of other revisions too, and the review's files no longer land in the working tree.
- `scripts/pr-comment.ts` builds the body from the two outputs (the review's Markdown, the check's JSON) without git or GitHub; `tests/pr-comment.test.ts` holds it to a change, no change, a failing check, no contract and a report over the limit. The README has the workflow.

The contract check.

- A baseline of known violations: `archdiff check --baseline [FILE]` writes the violations the code has now to `archdiff-baseline.json`, a file to commit — at the root, beside `archdiff.json` and `ARCHITECTURE.md` (the contract it excuses, read in the same review), not under `.archdiff/`, which is the cache and ignored; `"baseline"` in `archdiff.json` names another path. With the file there `check` exits 1 only on a violation that is not in it, lists the known ones apart with their count, and names the entries that no longer occur, so the file shrinks; `--no-baseline` holds the code to none. A violation is known by its rule, the importing module and the imported one, never by its line. The page's check (`GET /api/check`) and the contract check after an agent's run hold the code to the same file. An old repository can adopt a contract without a red CI (`src/baseline.ts`, `src/violations.ts`; `tests/check.test.ts`).
- Rules beside the layers: `"rules"` in `archdiff.json` state what the flowchart of `ARCHITECTURE.md` has no room for, and `check` holds the code to them, with or without a contract — `naming` (the files of a layer match a glob of the name or the path, or a regular expression), `threshold` (`max` and `min` on what `metrics` measures per module: `fanIn`, `fanOut`, `instability`, `abstractness`, `distance`, `cohesion`, `lines`; in one layer or everywhere), `cycles` (no import cycle, or no more than `max`: every import inside a cycle is a violation), `through` (a layer is reached only through the module named) and `forbidden` (a module, a glob, a package or a built-in is not imported from a layer, or from anywhere). Every violation has its file and line like an import against the layers, carries its rule's name in the report, in `--json` and in the baseline, and fails the check. A rule written wrong names its field, a field its kind does not take is refused, and a rule of a layer the repository lacks is a wrong call (exit 2). archdiff holds itself to two: no import cycle, and views that import nothing of Node (`src/rules.ts`, `src/violations.ts`).
- An agent's run is reported against the state before it: when the Chat tab starts a run the server records what the contract check finds (layers and rules, whatever the baseline says of them), and when the run ends, after the checks, its events say which violations the run fixed (`✔ the run fixed 1 violation`), which survive it (`• 2 violations survive the run (1 known, in archdiff-baseline.json)`) and which it added (`✘ the run added 1 violation`), each with its file and line (ten of a list, then how many more) — events of the kind `report`, shown in the transcript under the checks in their colours. A violation is the same one by its rule and its modules, so a moved line adds none; a run without a violation before or after says nothing (`src/checks.ts`, `src/violations.ts`, `web/src/chat.ts`; `tests/fixtures/fake-edit.mjs` is the agent that edits as its task says). The runner takes what follows a run from whoever starts it (`AgentRunner.start`), not once for every run.
- `check --json` lists every violation in `violations` with its `rule`, what is wrong (`problem`) and whether the baseline knows it (`known`), beside `stale` (the baseline's entries that no longer occur) and `baseline` (its file); `ok` says that no violation is new. A file written by `check --json --out` of an older archdiff has other keys, so `--out` takes it for someone else's: remove it once. On stderr and in the report a failing check counts *violations of the intent* (it counted *imports that go against* it).
- What reads the check follows it: the `check` tool of `archdiff mcp` answers with this report — the rules and the baseline with the layers — and the pull request's comment counts the violations the baseline does not list, says what breaks a rule in the check's own words with the rule's name, and counts the known ones in a line of their own (a check from an older CLI reads as before).

The blast radius of a change.

- `archdiff impact <path>[#<fn>]` and the view `impact:<path>[#<fn>]`: everything that depends on a module (the modules that import it or call into it) or on a function, a method or a class (the functions that call it; a class through any of its methods), walked backwards step by step to `--depth` (3), each dependent with its distance, its layer and what it reaches the subject through. The dependents written in a test file are told apart — what would catch the change, not what it breaks. `--types` counts type-only imports. Markdown with the picture, `--json` the same as data, `--format` the picture in any export format.
- A risk score of 0–100 per subject, its parts shown with the fact behind each: the dependents at any distance (30 points, full at 20), the layers they span besides its own (20, full at 3), the tests (20 when none reaches it, 10 when one does only through other code), the instability of its module (15 × I where something imports it) and its module's rank among the hotspots (15 for the module with the most calls in, 0 for one nothing calls into); under 34 low, under 67 medium, else high. It counts the dependents at any distance, so `--depth` cuts the list and not the score.
- The picture is placed by the view: the subject in the middle, a column per step to its right (the nearer, the darker), the tests that reach it on its left, every line the nearest way a dependent reaches the subject, routed in the room between two columns. A subject no test reaches is marked as the tests view marks it. A column keeps ten shapes and the picture `--limit` dependents; the Markdown lists them all.
- `archdiff impact --changed [--base REF] [--head REF]` and the view `impact` (among the overviews, *impact of the change*): every file changed since the base is a subject — a table of them by risk, each with its own sections, and one picture of what they reach together.
- On the page, a shape's right-click menu offers *Impact: what a change to it reaches* (a module, a function, a class), and the picture select lists it among the pictures of a subject.
- The computation is `impactOf(analysis, subject, { depth, types })` in `src/impact.ts`, a pure module of the views layer: the command, the view and the picture read it, and another reader can.

- Monkey testing (random taps, keys, options, hashes; fuzzed API and CLI) found and fixed: a plain view got siblings like `module:modules`; the depth field took -1; a shape's page was built with the default options, so a function of a module opened in place had no page; the file route refused a package shape's package.json. `drawio.ts` and `excalidraw.ts` imported each other; the colour scale moved to `export/colour.ts`.

- The Spec tab: the repository's OpenSpec specs and Gherkin features listed and shown; *spec this view* and *review all specs* have the agent write or review them (the task goes through the Chat tab), *validate* runs the OpenSpec CLI; `archdiff spec [--prompt view|all|update] [--validate]` in the terminal. A **copy** button beside the tabs copies what the active tab shows.
- The specification: `openspec/specs/*/spec.md` (OpenSpec: requirements and scenarios for analysis, views, page, intent, agent, exports, review, cli; all validate) and `features/*.feature` (Gherkin, the scenarios the tests run).
- Simpler code, same behaviour: git plumbing in `git.ts`, shape builders in `nodes.ts`, the steps after a view in `shape.ts`, the server's routes in `routes/pictures.ts`, `routes/agent.ts`, `routes/git.ts` over a context; the page's state, navigation and graph helpers in their own modules. The duplicate view select beside the title is gone (the canvas toolbar has it).

- A hub is a module a quarter of the picture's modules import, or forty of them, whichever is less (a quarter of a 500-module map was never reached).
- The `modules` view: the whole map, every module in its layer and every import. A picked shape's neighbours as chips above its page (click: pick here; Shift+click: its own view), the arrow keys walk them (→ ← along the arrows, ↑ ↓ along the lane) and Enter goes in: sideways navigation beside the deeper one.
- A project from scratch: `archdiff new <dir> --lang ts|js --template blank|lib|cli|api|web` writes the skeleton, `archdiff.json`, `ARCHITECTURE.md` (the intent) and the first commit.
- The intent as the contract: `ARCHITECTURE.md` with one Mermaid flowchart (subgraph = layer, node = module path and description, arrow = import) that archdiff reads and writes; the `intent` view draws it against the code (planned dashed, beyond the contract orange); `archdiff check` fails on an import between layers the contract does not allow; `archdiff import <file>` takes a document's flowchart; `archdiff intent --init` seeds one from the code; `--view` folds a drawing into it; archdiff.json's layers follow it.
