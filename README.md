# archdiff

Live diagrams of a TypeScript, JavaScript, Python, Rust, PHP, Go, Java or C# repository, computed from the code: the layers and the imports between them, every module with what it imports and what imports it, the call tree from every entry point, the map of what the analysis cannot see, and the architectural diff of a change for reviewing pull requests. Algorithmic (tree-sitter and graph algorithms, no model), fast (a fact cache keyed by file content, parallel parsing), one npm package.

```bash
npx @ivlad003/archdiff web      # the diagrams of the current repository in a browser
npx @ivlad003/archdiff review   # the architectural diff against the main branch, as Markdown + Mermaid
```

The package is `@ivlad003/archdiff` on npm (npm refused the bare name as too close to `arr-diff`); the command it installs is `archdiff`, so after `npm i -g @ivlad003/archdiff` every example below reads as written.

## Views and detail

- **layers** — one shape per layer with its module count, one line per import direction with the count.
- **modules** — the whole map: every module in its layer's lane and every import between them. Big by nature: hubs become badges, the tail folds by directory, *lines of weight ≥ N* thins it; the path, focus and find tools work on it like on any picture. Above six lanes the lanes lie as columns (blocks across the picture, in the order the lines flow) rather than as rows; `--lanes rows|columns` and the toolbar's *lanes ↔* choose.
- **layer:name** — the modules of a layer; `--depth 1` (default) adds the modules of other layers they import or are imported by.
- **dir:path** — the modules of a directory (and below) with their neighbours: the rung between a layer and a module.
- **module:path** — what the module imports (files and packages) and what imports it; `--depth 2` goes one step further.
- **inside:path** — the functions, classes and methods of a module and the calls among them, each module a lane; `--depth 1` (default) adds the functions of other modules they call. What a file does, as a map.
- **sequence:path#fn** — the calls from a function as a sequence diagram: the modules on the way across the top (at most 12 lifelines; the rest share one), every call a numbered message in the order the code makes them, a call repeated in a row as one message "×N", and the calls under a branch or a loop framed as fragments — an `if` with its `else`, a `switch`'s cases and a `try` with its `catch` as one `alt` with its arms, a loop as `loop`, a lone branch as `opt` — nested up to three deep; an operation of an API (SCAPI's `getBasket`) is a message to its family's lifeline; a call into a hub module (a logger most of the repository imports, unless its functions reach an operation within three calls) is drawn and not followed, so the business calls stay in view (`--no-hubs` follows it); past the limit the operations and the calls leading to them stay and the deepest of the rest leave first, and past twelve lifelines the modules fold before the API families; `--depth 1` reads as the function's own logic — its branches as fragments, its calls and operations as messages (Mermaid `sequenceDiagram` in the Markdown).
- **path:path#fn** — from an entry point to the storages only: every branch that leads to no store, database, cache or operation of an API is pruned.
- **type:path#Type** — where a type flows: the functions that produce it, consume it or transform it, storages marked.
- **usage:path** — the exports of a module and who uses each from outside; an export nothing uses says so (`contract:` is the old name: the contract is ARCHITECTURE.md).
- **classes**, **classes:path**, **classes:dir** — the class diagram: every class, interface and object type as a box with its fields (`+`, `-`, `#`) and methods, `extends` and `implements` as lines, `has` for a field typed with another class and `uses` for the calls a class's methods make to another class, modules as lanes; Mermaid `classDiagram` in the Markdown. A box's second tap opens the module's inside.
- **cycles** / **cycle:path** / **cycles:fns** / **cycle:path#fn** — modules importing each other (or, with `fns`, functions calling each other across modules), one lane per strongly connected component, with the fewest and lightest lines whose removal breaks the circle drawn red and dashed ("cut: 1 import"); layers importing each other get a lane of their own; `--types` counts type-only imports too, dashed.
- **metrics** / **metrics:layer** — coupling and cohesion as numbers: per module Ca (who imports it), Ce (what it imports), instability I = Ce/(Ca+Ce), abstractness A, the distance from the main sequence D = |A+I−1| (orange when far and coupled: the zone of pain, concrete and depended upon, or of uselessness, abstract and depending on everything) and the cohesion of its functions (1 when they form one group by calls, shared callees and shared types); Mermaid: a `quadrantChart` of I against A; `--overlay instability` shades any picture by I and marks the unstable modules others depend on.
- **machines** / **machine:path#name** — state machines: the explicit ones a library declares (XState's `createMachine`, javascript-state-machine, Python's `transitions`) and the implicit ones written with literals — a field set to two or more literal states and compared or switched on; its transitions are the assignments under a `case` or an `if` on the same field (`case "new": order.status = "paid"` is new → paid, in `pay`), an assignment under no such guard comes from any state, and a union type naming the states declares the ones never set (dashed). Mermaid: `stateDiagram-v2`; Markdown: the states and a table of transitions with `file:line`.
- **matrix**, **matrix:dir** — the dependency structure matrix of the layers, or of a directory's modules: rows import columns, counts in the cells, imports against the order in red. A matrix scales where a graph of the same size tangles.
- **events** — emitters → event names → listeners (`emit`/`publish`/`dispatch` and `on`/`subscribe`/`addEventListener` with a literal name), and messages: `postMessage`/`sendMessage`/`send` of an object with a `type` is an event of that type, handled by every function that compares or switches on a `type` with that value — a browser extension's side panel, service worker and host, or a worker and its page, joined by what they say to each other.
- **messages**, **messages:path** — what the parts say to each other as a sequence diagram: the modules as participants, every typed message an arrow from its sender's module to the module of each function that handles it (one per sender, handler and type, counted when sent from several places); a module as the scope keeps the messages it sends or handles. Mermaid `sequenceDiagram`.
- **apis**, **apis:Family**, **apis:path** — the operations of an external API the code calls (SCAPI, the Salesforce Commerce API: `clients.shopperBaskets.getBasket()`), by family and by module; a family opens to its operations and the functions calling each; the OCAPI hooks of a cartridge (hooks.json) are joined to the resource they modify — a GET hook to the `get…` operations.
- **postman**, **postman:file** — a Postman collection of the repository (every `*.postman_collection.json` git lists, and the files `archdiff.json`'s `postman` names) against the code: each request in its folder's lane, joined to the modules calling the operation it names (matched by method and path, a variable of either — `{{basketId}}`, `:basketId`, `{basketId}` — standing for any value, the route that agrees most taken); a request the code never calls is marked removed (red), an operation the code calls that the collection lacks is marked added (green) in the API's lane. A collection `archdiff postman` wrote reads back whole.
- **tests** — which modules the test files import; a module no test imports is marked.
- **hotspots** — every module as a box sized by its lines and shaded by the calls into it from other modules.
- **packages** — the package.json files of a monorepo as a system: declared dependencies, imports between packages, and imports no package.json admits.
- **timeline** — the drift of the architecture commit by commit as bars (`--base`, `--head`), red when a commit coupled two layers; a commit opens its own change. At one commit of the range (`--at SHA`; the slider on the page) it is the whole map of the code as it was then, with what the commit did marked.
- **changes**, **changes:layer:dir** — the board of the uncommitted changes: what the working tree changes against the last commit (against nothing before the first one), the changed modules in a lane per group — the layer, then the directory — that says what the change comes to there, the groups in the order a reviewer reads them: the entry points first, then what they import and call. A group's own picture opens its modules to the declarations the change added, changed and removed, with the imports and calls it added and removed, and its page ends with the diff of its files as text. On the page (`c`) a bar walks the groups (`.` and `,`), and the board is drawn again whenever a file changes or a commit is made.
- **branches** — the branches as a picture: a lane per branch, the base on top (develop, main or master, or `--base`), time from left to right; each branch leaves the commit it forked from — on the base, or on the branch it was started on — with how far it is ahead and behind; a branch with nothing of its own is named on the commit it points at. On the page, a tap on a commit shows its message and files, a double tap opens its change, and its menu gives the code at that commit, the code of its branch and the branch's review.
- **commit:sha** — one commit's own change against the commit before it (a first commit against nothing), as a review: the modules, functions, imports and calls it added, removed or changed, and the layer couplings it introduced.
- **calls:path#fn** — the call tree from a function, `--depth 3` by default; a hexagon is a call archdiff could not follow, with the reason. Double-click a function on the page to open its own tree.
- **focus:path#fn**, **focus:path** — everything joined to one shape, across the modules: for a function, what calls it and what it calls (`--depth` steps each way, calls and references alike), each module a lane; for a module, its functions with their callers and callees in other modules, and the modules joined to it by an import alone. The page opens it from a shape's right-click menu or the picture select.
- **impact:path**, **impact:path#fn**, **impact** — the blast radius of a change, before it is read: everything that depends on the subject, walked backwards step by step (`--depth 3` by default) — for a module the modules that import it or call into it, for a function, a method or a class the functions that call it (a class through any of its methods) — with the tests among them told apart: they are what would catch the change, the rest what it could break. The picture is placed with the subject in the middle, a column per step to its right (the nearer, the darker) and the tests that reach it on its left; every line is the nearest way a dependent reaches the subject. The risk is a score of 0–100 whose parts the Markdown shows with the fact behind each: the dependents at any distance (30 points, full at 20 of them), the layers they span besides the subject's own (20, full at 3), the tests (20 when none reaches it, 10 when one does only through other code), the instability of its module (15 × I where something imports it) and its module's rank among the hotspots (15 for the module with the most calls in) — under 34 low, under 67 medium, else high; it does not change with the depth. `impact` without a subject (`archdiff impact --changed`) takes every file changed since the base as a subject: a table of them by risk, and one picture of what they reach together. `--types` counts type-only imports as dependencies; a column keeps ten shapes and the picture `--limit` dependents, the Markdown lists them all. On the page, a shape's right-click menu opens it.
- **whatif:move:path>to**, **whatif:delete:path**, **whatif:split:path#fn,fn>new** — a change supposed, not made (`archdiff whatif …`): the picture a review would draw of it — the module removed at its old path and added at the new, a deleted module with the modules whose import breaks marked, the new module of a split with the imports that follow the functions — and the report beside it. A move's target that is no source file (or ends in `/`) is a directory, and the file keeps its name; the module's layer is the one `archdiff.json` gives the new path, so a move across layers shows the dependencies between layers it would add and whether the contract allows them. A split's imports follow the code: an importer imports the new module where it binds or calls a moved function, the new module takes the old one's imports its functions use, and the two halves import each other where one calls the other — which is how a split closes a cycle, and the report says so. It supposes the change is made well (the importers' paths rewritten): it says what the architecture would be, not what the compiler would say. On the page, a module's right-click menu supposes it deleted or moved, a function's split off; the picture opens as a review does and is not drawn on.
- **logic**, **logic:path#fn** — the business logic of a function as a flowchart: a diamond per branch or loop with the condition as the code writes it (`if`, `switch`/`match` with one arrow per case, `for`/`while` with `each` and `done`, `try` with `ok` and `error`), a box per run of plain statements, an ellipse per exit (`return`, `throw` in orange, the end of the body); the Markdown lists every path from the start to an exit as a rule — the conditions taken, the calls made, how it ends — so the rules can be read and checked. `logic` lists the functions with branches, the most branching first. The body is read from the file when the view is asked for (TypeScript, JavaScript, Python, Go, Java, C#); a step that calls one function of the repository opens that function's logic on a second tap.
- **coverage** — the modules with blind spots, biggest first.

Entry points come from the code and the frameworks: exported functions under `bin/`, a browser extension's listeners (the functions a script hands to `chrome.*.on*.addListener` or a port's `onMessage.addListener`, labelled with the role `manifest.json` gives the script: background, content script, side panel, popup, options, devtools), functions named `main`, React Router route modules (the `loader`, `action`, `clientLoader`, `clientAction`, `default` and `ErrorBoundary` exports of files under a `routes/` directory), SFCC cartridge hooks (`cartridges/*/hooks.json`), the files named by `entries` in `archdiff.json`, and exported functions nothing in the repository calls.

## The page

One canvas, Excalidraw, in its hand-drawn style. Reading: tap a shape for its code and Markdown (a module's declarations fold open to their calls and code), Shift+tap or Ctrl+tap more shapes to select several (two light the shortest chain of lines between them; more list themselves with the lines among them in a strip under the tabs, with *ask about them*, *dim others* and *clear*), hold Alt and press a shape or a line for a peek — its lines alone, lit, the shapes at their ends kept and the rest faded, until the button or Alt is released — right-click a shape, a line or the empty canvas for its menu (open, focus, impact, logic, the other pictures of the subject, a what-if of it — a module deleted or moved, a function split off — add to the selection, ask the agent, dim, code, copy the name), tap a line to light it with its two ends and read where it leads — the imports and calls behind it, each with its `file:line`; where several lines run together the panel lists them all to pick from, and *follow* (or Shift+tap) lights the whole chain the arrows lead on to; the line under the pointer lights as you hover, and a tap on nothing puts every light out — tap a shape again to open its own view (a layer → its modules, a module → inside it, a function → its calls, the function a call tree starts from → its logic; a shape that opens nothing says so); a picture with nothing to draw says why in the middle of the canvas, and one that cannot be drawn clears the canvas and says why; the select beside the title switches between the pictures of one subject (dependencies or inside; call tree or sequence), drag to pan, wheel to zoom, `0` fits, Backspace goes back. Big views fold their tail by directory into "… N in src/x/" shapes (a tap opens that directory) so the picture stays readable — above 40 shapes by default, since a picture reads best well under that (the whole map, `modules`, above 200: it is there to show every module; the field *fold above* shows the view's own number); the Markdown lists everything. A module much of a picture imports — a quarter of its modules, at least six and at most forty of them (a logger, the shared types) — is drawn as a badge "+ log.ts" on its importers rather than as a fan of lines across everything; a picture of fewer than eight modules keeps every module, a shape a review marked stays drawn, `archdiff.json` `"hubs"` sets the numbers, and `--no-hubs` or the *hubs as badges* box draws them all; *lines of weight ≥ N* leaves out lines standing for fewer than N imports or calls. Every picture carries the one question it answers (the title's tooltip, the first line of its Markdown) and the commit it was drawn from (in every export). Arrows leave a shape on the right, run in the gap before the next column and enter on the left; a backward arrow goes around below; a line's label sits on the line, clear of the shapes and the other labels. Breadcrumbs in the title (layers › layer › directory › module › function) walk back up; a picture is fitted whole below the toolbar and clear of the minimap, and fitted again when the window or a panel changes the canvas's size (a picture too big even at the smallest zoom starts from its beginning, and the line under it says so); a view the reader zoomed or panned comes back where it was left (remembered in the browser; `0` fits it again and forgets); the page reloads when a source file changes (`--no-watch` turns that off; when the system has no file watchers left, the server's first line and the stats in the header say the page does not follow the code); ◐ switches the dark theme.

**The canvas toolbar** (top left of the picture) is the quick way: a *picture* select switches between the pictures of the current subject and the overviews; *minimal · normal · full* set how much shows at once (depth, fold, line weight, hubs together; *full* goes one step deeper than the view by itself) and *depth −/+* step the depth from the view's own (3 for a call tree; off on a view that goes no depth, like the layers); **mix** (`m`) opens a tapped module in place — it becomes a lane of its own functions, and the lines into it land on the functions the sources actually call, the rest on a "rest of the module" shape (`--expand a.ts,b.ts` in the terminal; *close opened* folds them back); **dim** (`d`) fades everything but the tapped shape and its neighbours (the menu's *Focus* is the other way round: a picture of everything joined to the shape, across the modules). Also there: *find* (`/`) lights the shapes matching a name and Enter centres the first (a name the picture does not show opens the view whose subject it is); *lanes* ticks lanes in and out of the picture (`--hide-lanes` in the terminal); **split** (`s`) opens a second, independent picture beside the first — another view, another branch, the same page embedded (one above the other below 1520 pixels, too narrow for two canvases); *lanes ↔* (`l`) flips the lanes between rows and columns; **minimap** hides or shows the picture in miniature at the bottom right (on by default, remembered; the shapes and lines of the whole picture, the viewport as a box — tap or drag it to move); **project** (`p`) opens the project map over the canvas: the whole repository as dots coloured by layer and sized by lines, every import a line, laid out by forces like a vault in Obsidian and fitted whole (a dot pushes only the dots near it and every dot is pulled to the middle, so a script nothing imports stays beside the rest); hover names a dot and lights its neighbours, the dots of the current picture wear a ring, a click opens the module, Shift+click everything joined to it, a double click its inside, the layer chips hide layers, the search box finds a module (a repository over 400 modules is folded to directories); a Shift+tap on a second shape lights the shortest chain of lines from the shape tapped before and lists it. Under a shape's corners, small counts say what lies beyond the picture's depth — ◂ 3: three modules (or functions) import or call it from outside the picture, 5 ▸: it imports or calls five there; a tap on a count picks the shape. A strip under the tabs shows a picked shape's neighbours in this picture as chips (← what imports or calls it, → what it imports or calls), then the ones beyond, dashed (a click opens the neighbour's own picture, Shift+click its focus): a click picks the neighbour here, Shift+click opens the neighbour's own view; the arrow keys walk the same way (→ along an arrow, ← against it, ↑ ↓ along the lane) and Enter goes into the picked shape — so the diagram is walked sideways as well as deeper. In the options, *only the changed and their neighbours* (`--only-changes` with `--changes`) cuts a review picture down to what the change touched, and *only the changed files* (`--changed`, `changed=1` in the link) keeps the shapes of the files changed since the base alone, with the marks — a layer by the files in it, a folded tail by the files it stands for, a package or an event when a line joins it to one — while the views list and the folder tree list those files alone (`archdiff views --changed [--base REF] [--head REF]` in the terminal, every view with a note on stderr outside git; the header says how many files changed since which base, or why git could not say). The view's own subject stays whatever changed; a grid, a flowchart, a timeline or a comparison stays whole and its reason says the cut does not apply there.

**show as** (the toolbar's second select, `as=` in the link) is how the centre shows the view: the **canvas**; the same picture in **3D** — each lane a terrace raised by its order (the top lane highest), each shape a block with its footprint of the canvas in its colours, each line a tube arched from block to block with an arrowhead, every label floating above its block; drag to orbit, wheel to zoom, right-drag to pan, tap a block for its code on the right, double-tap it to open its own view, `0` fits — its **Markdown** page, or the **code** of its subject (the file the view names, a function's lines marked; an overview shows its page instead). The 3D view is loaded when first asked for. Drawing, mix, dim, split and the project map need the canvas.

The left panel lists the views in groups, or (**tree**, `t`, remembered) shows the repository as a folder tree: the layers, their directories as folders, the modules as files, and a module's functions once its caret is opened (read from its inside picture); a tap on an entry opens its view with the centre as it is — in the Markdown presentation the pages read like a book with the tree as its table of contents — the entry of the current view is lit with the folders above it opened, which folders are open is remembered, and the filter finds entries with their folders open. In the lists and the tree alike, the files the picture shown now is of carry a dot — the navigation says where the diagram is — and *● N in picture* over the filter cuts the panel to those files (remembered).

**Hints, and two languages.** Every button, tab and mark says what it is for in a bubble beside it, a moment after the pointer rests on it (and for the keyboard's focus). The page speaks English or Ukrainian: *Language* in the settings window (the ⚙ of the header), kept with your settings so it holds for every repository. The page's own words are translated — buttons, hints, notes, the chat's commands and their help, the legend; what archdiff writes about the code (a picture's page, the Mermaid, the names on the canvas) stays as the command line prints it. While the server is asked for something a thin bar runs under the header.

**The panels give way to the canvas.** Each folds away and back — the header's ☰ and ▤, the tabs on the centre's edges, Ctrl+B and Ctrl+] — and is as wide as you drag its edge (dragged well past its narrowest it folds away; a double click gives the width it came with); both are remembered. Where the window has no room to dock a panel beside a canvas of 730 pixels (under that Excalidraw folds into its phone layout) — the two panels in a window under about 1430 pixels, the views alone under about 1010 — the panel is a *drawer*: away until asked for, then laid over the canvas, which keeps its width and the picture's place. The details' drawer opens by itself for what a tap picks and goes when nothing is picked any more (a tap on nothing, Escape); opened by you, it is yours to close. A shape picked where the drawer opens is moved clear of it with its picture, which goes back where it was when the drawer does. The views' drawer opens with ☰ or `v` and goes once a view is picked. **⤢ full** at the end of the title (`f`, remembered) makes both panels drawers on any window: the picture has the page's whole width, and what you tap still comes to be read. A docked panel you folded away stays away, and its tab is marked when a pick has something to read. On the toolbar, **tools** folds everything but the picture, *show as* and *find* (a canvas under 860 pixels folds them by itself; a tool that is on — mix, dim, split — stays in sight); **legend**, beside *full*, hides the legend, which lists the kinds of shape and line of the picture shown and the marks of a change on it, each drawn as the canvas draws it. The menus of the page (options, export, lanes) close on a press outside them and on Escape, one open at a time, and the note at the top of the Chat, Flow and Spec tabs folds away (remembered).

The keys, outside the fields and the editor and without Ctrl, Alt or Cmd: `/` find a shape, `v` filter the views, `t` the views as lists or as the folder tree, `o` the options, `p` the project map, `0` fit, Backspace back, ← → ↑ ↓ walk, Enter go in, `s` split, `m` mix, `d` dim, `l` the lanes, `[` `]` the previous and the next branch, `b` the branches, `c` the board of the uncommitted changes, `.` `,` the next and the previous step of what is walked (the steps of a tour being played, else the groups of the board, else the commits under the slider), `k` play and pause the commits, `e` edit, `f` the full canvas, Escape clear (with an open drawer; a menu and the project map close first); Ctrl+B and Ctrl+] fold the side panels (remembered), Ctrl+S saves a drawing. A picture read from git (a review, a comparison, a commit, the branches, the uncommitted changes) is not drawn on: its keys of the tools are off. The options menu also holds the presets of who reads — *reviewer* (the changes and the tests overlay), *newcomer* (one step deep, thirty shapes), *architect* (the heat, sixty shapes, lines of weight two) — and *remember as defaults* keeps the options for every link that leaves them out, in this browser.

**options ▾** (or `o`) holds what the terminal flags hold: the depth (no ceiling: past 12 the field turns orange and the picture says first that it may be big and slow to draw; `--depth 20` says so on stderr too), the fold limit, the weight of the lines, hubs as badges, the packages, the overlays and the Mermaid type of the Markdown and the export (the types that draw one kind of view, a machine's state diagram and the timeline's gitGraph, are greyed out elsewhere); a *preset* sets them for a reader at once — *reviewer* (changes since base, untested modules), *newcomer* (depth 1, fold above 30), *architect* (heat, lines of weight 2 and more, fold above 60). Overlays lay one more fact over any view, in any mix — *changes since base* (the review's marks, `--changes`), *untested modules* (what no test file imports, in orange), *storages* (⛁ with what they hold), *heat* (every shape shaded by the calls into it, the count in its label), *instability* (every module shaded by Martin's I, the unstable ones others depend on in orange), and three read from git, from the commits of the picture's range (the base to the head; on the main line itself its last 200 commits): *churn* (every module shaded by the commits that changed its file), *change coupling* (a dashed line between two modules whose files changed in one commit at least twice, with how often — where no import joins them, they are coupled where the code does not say so) and *ownership* (every module named and tinted for the author of most of the commits that changed it); `--overlay tests,storages,heat,instability,churn,coupling,ownership` in the terminal. Every option travels in the link, so a link shared in a pull request opens the same picture; a value the options table refuses (`limit=1.5`, `overlay=nope`, an old link's) is left out alone, the rest of the link kept, and the line under the picture names it. *remember as defaults* keeps the current options in this browser for every link that names none, *reset* forgets them and sets every option of the picture back, the toolbar's and the lanes menu's too (opened modules, hidden lanes); both say so once the picture is drawn again. *changes since base* needs git: elsewhere the picture is drawn without the marks and says why.

Drawing (`✎ edit`, or `e`): move shapes, draw with the pencil, write notes, take a PNG or SVG of the drawing or of the selected shapes. `save` writes `.archdiff/layouts/<view>.json`; the live diagram and every export then follow the saved places — the lines are routed around every shape on a grid of their sides when shapes left the layout's columns, and a computed shape never sits on one placed by hand — and `re-layout` merges a fresh picture of the code into the drawing — shapes that still exist keep their place, your strokes stay, stale shapes go. Commit the layouts to share them in a pull request, or ignore `.archdiff/` to keep them local.

The Code tab shows the file of the shape picked in the colours of its language, under a line that names the file and stays while the code scrolls; it comes to the front at the press and says what it is reading until the file lands. The Markdown panel renders (a `raw` toggle shows the text to copy); `file:line` in it opens the code. A page is a navigation too: its sections fold by their headings (a fold is remembered across pages with that heading), a module or a function named in bold opens its view with the centre as it is, and a caret on a module's bullet unfolds its functions, each opening its view or its code. The Flow tab, on a call-flow view, lists the steps in call order with their parameter and return types and the storages on the way (modules named `db`, `store`, `repository`, `cache`…, or importing `pg`, `prisma`, `redis`, `mongoose`…). Attach a mock input to the entry and mock contents to the storages — typed by hand, or *generate mocks* from the types, or from a description of the scenario when an agent is configured — and values are carried to parameters and properties of the same name, so the flow reads with data in it. *▶ play* lights the predicted steps on the diagram one after another. *▶ run* runs the entry for real: the repository's own TypeScript or JavaScript runs in a child Node process under Node's permission model (reads only, no child processes), every function traced at the start of its body, the storage packages (a database client, `node:fs`, `fetch`) replaced by recorders that answer from the mocks; the functions entered light up green, the predicted ones never reached dim, and the report under the steps lists the storage calls and the result or the error (`archdiff run calls:… --input '{…}' --storages '{"node:fs": {…}}'` in the terminal). What the predicted flow claims is what the types and the names say; what the run shows is what happened.

**The page from the Chat tab.** A line that starts with a slash, in the question row, the task box or the follow-up, is a command of the page; it needs no agent, it is suggested as you type, and what it did stands in the transcript. `/help` lists them all: `/view layers` or `/view checkout action` (a key, or words of a title), `/as 3d`, `/detail full`, `/depth 2`, `/overlay heat, tests`, `/changes on`, `/preset reviewer`, `/mix orders store` (modules opened in place) and `/unmix`, `/select`, `/find`, `/review main feature-a`, `/compare a b`, `/commit 1a2b3c4`, `/board`, `/impact src/db/store.ts`, `/logic validate`, `/split calls:src/routes/checkout.tsx#action` (another diagram beside this one), `/export drawio`, and the tab's own `/ask`, `/agent codex`, `/stop`, `/check`, `/code`, `/diagram`, `/doc`, `/settings`. `/grep saveOrder` searches the code and `/diff total` the lines the change added and removed — a capital makes the case count, a regular expression goes between slashes (`/grep /save\w+\(/`) — each line with its `file:line`, which opens the code, and the shapes of the files found lit on the picture (`archdiff grep` in the terminal). An agent drives the page the same way: a fenced `archdiff-do` block in its answer, one command a line, is run for you — the commands that show something, never one that draws, changes a setting or starts a run — so "show me where an order is saved" answers with the picture as well as the words. Claude Code is also handed archdiff's MCP server with every run (below), and searches the code and the change through it.

**An explanation, step by step.** *explain* — the button of the Chat tab, *Explain it, step by step* in a shape's menu and in the picture's, *explain* on the strip of a selection, or `/explain how an order is saved` — has the agent explain the picture, the shapes picked or what you name, and answer with a tour instead of a page of prose: three to eight steps in the order to read them, each a view, the shapes to look at on it — a way through them lit, line by line, when they are one — and a note that says what the step shows, how it works and why it is so, with the `file:line` the code says it at. The page plays the tour at once: the picture changes, the shapes light, the note stands under the title, ‹ and › (`,` and `.`) step back and forth; it is kept in the *tours* menu with the others, to be played again, shared as a link or written out with `archdiff tour`. `/path routes lib db` lights a way through shapes by hand.

In the Chat tab, the first row asks a question: about the picture on the canvas (its Markdown and Mermaid go along, with the options as shown) or about the shapes picked on it — the selection strip's *ask about them* and the menu's *ask the agent about it* put the shapes in the row as chips — and the agent is told to answer without changing a file; without an agent the question with its context lands in the task box, to be copied to any assistant. The transcript is compact: a question, its tool calls and thoughts folded under one line (click to unfold), the answer rendered, the checks, the run's report and the exit under it. `@` names what the diagrams know — `@module:src/lib/orders.ts`, `@fn:src/lib/orders.ts#placeOrder`, `@layer:db`, `@dir:src/lib`, `@flow:src/routes/checkout.tsx#action`, `@type:src/lib/orders.ts#Order`, `@logic:src/lib/orders.ts#placeOrder` (the flowchart and its rules), `@view:<key>` (any picture) — with suggestions as you type; each tag is sent to the agent with its context (the shape's Markdown: declarations, calls, callers, code). While the agent works, the shapes of the files it reads or edits light up on the diagram. When it finishes, archdiff runs the contract check and the commands `archdiff.json` names in `"checks"` (`npm test`, `npm run typecheck`, `npx -y @fission-ai/openspec validate --specs`…) and streams their results into the tab (✔ / ✘ with the output's tail); *run checks* does it on request. A run is also reported against the state before it: when it starts, archdiff records what the contract check finds — the imports against the layers and the violations of the rules, known to the baseline or not — and when it ends says under the checks which of them the run fixed (✔), which survive it (marked *known* where the baseline lists them) and which it added (✘), each with its file and line (the first ten of a list, then how many more); a violation whose line only moved is the same one, and a run that neither started with a violation nor left one says nothing. Claude Code is allowed to run exactly those commands, archdiff itself and the OpenSpec CLI (`--allowedTools`), so it can verify its own work before it answers.

## In Chrome, beside GitHub

`chrome/` holds an extension that puts archdiff beside a page of GitHub: a package of its own, installed from its build ([chrome/README.md](chrome/README.md) says how; it is in no store, and no part of the npm package). With `archdiff web` running in your checkout, open the repository on GitHub and press the extension's button: Chrome's side panel shows the picture of what the tab shows. A pull request and a comparison (`/compare/main...feature`) are the review from where the head left the base — their merge-base, as GitHub lists their files; a branch off the main line is reviewed against it; the main line and a file are their code; a commit is its own change. A select switches between the pictures of the subject — the review, the layers with the change marked, the impact, the commits one by one, the code of the head — and a tap on a shape sends the tab to that file on GitHub: in the pull request's list of files when the change touched it, else at the head's revision and its lines.

The extension draws nothing and reads none of the code. ## Reviewing branches

The header's **head** field is the code the page shows: any branch, tag or commit (the branches are offered as you type, `[` and `]` step through them), read from git without a checkout — every picture, the views list, the Code tab, the coverage and the project map follow it, and the title ends with "@ branch"; empty is the working tree (`diagram <view> --head REF` in the terminal). `b` shows the branches as a picture, to see where each one stands and open its code, its review or one of its commits. `review` on the page opens the branch bar: a base (develop, main or master by default, or any branch) and the heads — the working tree, the current branch, any other local or remote branch — as a list under *branches ▾*, a row a branch with the day and the subject of its last commit; type a part of a name or of that subject to find one among a hundred, Enter ticks the first found, and the ticked heads stand in the bar as chips. One head is the review; tick two or more and `compare` draws every module any head touched — each head from where it left the base (their merge-base, named in its row), as its pull request would show it, so what the base gained since is not read as the head's doing — labelled with what each head did to it (`+ feature-a  ~ feature-b`, or "every head" when they all did the same; a module's page lists what each head did to it), the imports each head added or removed labelled with the head, and a table per head with the layer couplings it introduced. A bar below lists the commits of the range; pick one, step with ‹ › (`,` and `.`), drag the slider over them or press ▶ (`k`) to have them follow by themselves (slow, normal or fast, remembered), to see that commit's own change against the one before it. The **timeline** has the same bar: there a commit is the code as it was then — the whole map, with what the commit added, changed and removed marked — so the slider plays the architecture growing; *churn*, *coupling* and *owners* beside it lay over the picture what the commits up to that one say of the files. A tap on a shape in a review shows the commits that touched its file. In the terminal: `archdiff branches`, `archdiff compare --base develop --heads feature-a,feature-b,WORKTREE`, `archdiff history`; the next section has the GitHub Action that keeps the review on every pull request.

**The uncommitted changes** have a board of their own (`c`, or *uncommitted changes* in the picture select; `archdiff diagram changes` in the terminal): the working tree against the last commit, whatever the base and the head fields say. The changed modules are grouped by what they are part of — the layer, then the directory — and each group's lane says what the change comes to in it: `lib · src/lib/ — modules +1 ~1 · functions +1 ~1 · imports +2 · calls +3`. The lanes are in the order a reviewer reads a change: the modules execution starts from (a route, a hook, a `main`), then what they import and call, step by step. The bar under the title walks them: ‹ and › (`,` and `.`) step from the whole board to each group's own picture — its modules opened to the functions the change added, changed and removed, the imports and calls it added and removed in green and red — with the group's diff on the Markdown tab, as text. The page draws the board again whenever a file is saved and when a commit is made (which empties it), so it can be left open beside an agent at work, and read through before committing. The Chat tab stays on the board: a question about the picture is a question about the change.

**Down to the logic and the lines.** A picture of a change says which modules and functions it touched; the pages say how. The page of a changed module ends with a line for each of its functions the change touched — `logic:src/lib/orders.ts#placeOrder — steps +2 −0 ~0, rules +2 −1` — and in a review a tap on that name opens the function's flowchart with the change laid over it: the steps that are new in green, the ones that read otherwise in orange, the steps and the arrows that are gone dashed in red where they hung, and above the rules a list of what came and went — every step, and every rule (a path from the start to an exit) the function gained or lost. `archdiff diagram logic:<path>#<fn> --changes [--base REF]` prints the same; *changes since base* in the options lays it over any function's logic. A statement is what is matched, not a box, so one line added to a function marks the box that holds it and nothing after it. The Code tab, on any picture of a change (a review, a commit, the uncommitted changes, *changes since base*), shows the change on the file itself: the lines that came tinted, the lines that went where they stood, struck out.

## On a pull request: the GitHub Action

`action.yml` at the root of this repository puts the architectural diff on the pull request itself, as one comment that is rewritten on every push: what the head added, removed and changed since it left the base — the counts, the dependencies between layers that appeared and went, the Mermaid picture, and every change by kind, folded — under the verdict of `archdiff check` against `ARCHITECTURE.md` with its violations. The same goes to the job summary, and the job fails when the check does.

```yaml
# .github/workflows/archdiff.yml
name: archdiff
on:
  pull_request:
permissions:
  contents: read
  pull-requests: write # the comment
jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0 # the merge-base needs the history
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - uses: Ivlad003/archdiff@v0
        # with:
        #   base: develop          # default: the pull request's base ref
        #   fail-on-check: "false" # default "true": the job fails when archdiff check does
        #   comment: "false"       # default "true"; "false" writes the job summary only
        #   working-directory: packages/api
```

| input | default | what it does |
| --- | --- | --- |
| `base` | the pull request's base ref | The ref the head is compared with, from where it left it (their merge-base), so what the base gained since is not read as the head's doing |
| `fail-on-check` | `true` | Fail the job when `archdiff check` finds an import between layers that `ARCHITECTURE.md` does not allow |
| `comment` | `true` | Keep the comment on the pull request; `false` writes the job summary only |
| `working-directory` | `.` | The directory archdiff runs in: the repository, or one package of it |

`fetch-depth: 0` matters: the merge-base needs the history, and a clone without the base stops the job with a message naming the fix. The comment needs `pull-requests: write`; a pull request from a fork gets a read-only token, so there the review is in the job summary alone, with a warning. The check is of the whole code at the head: an import against the contract that the base already had fails it too, and without an `ARCHITECTURE.md` that names layers there is nothing to fail on, which the comment says (`archdiff intent --init` writes one from the code). A pull request that changed no module, function, import or call gets one line saying so instead of an empty picture. GitHub takes no comment over 65 536 characters: past it the picture stays and the lists are cut, each to the same number of its first items, with a count of what was left out; the job summary has them all. The action restores `.archdiff/` from the run before, so a review after the first takes about a second. [docs/ci.md](docs/ci.md) has the commands for any other CI.

## Guided tours

A tour walks a reader through the pictures: a list of steps, each a view with its options, the shapes selected on it and a note in Markdown. **tours ▾** in the header lists the tours of the repository, plays one, and starts the recording of a new one from its name. While a tour is open a bar under the title holds its steps and the note of the one shown; ‹ and › (`,` and `.`) walk it. To record, open any picture, set it as it should be seen, pick the shapes to point at, press *+ add step* and write the note — the step keeps the link of the picture and the selection; *✎ note* rewrites a note, *remove* takes the step out, and a press on the tour's title renames it. *link* copies the address of the step: `#tour=<name>&step=N` opens that picture, selects its shapes and shows its note, in any browser — a link of a tour takes none of the defaults a browser remembers. Walking off a step is fine: the bar says so, and the list leads back.

A tour is a file, `.archdiff/tours/<name>.json`, or `<dir>/<name>.json` when `archdiff.json` names `"tours": "<dir>"` — a directory to commit, so an onboarding tour travels with the code. `archdiff tour <name>` writes it as Markdown, each step with its note and its picture as Mermaid, for a README or a pull request.

## A project from scratch: the intent

`archdiff new my-app --lang ts --template api` (templates: `blank`, `lib`, `cli`, `api`, `web`) writes the skeleton that ties nothing to a framework — package.json, tsconfig, archdiff.json with the template's layers, `ARCHITECTURE.md` with the template's intent, the first commit on `main` — and nothing else: the libraries are the agent's to add from the drawing. `ARCHITECTURE.md` is the contract: a Markdown file with one Mermaid flowchart where a subgraph is a layer, a node is a module (its label the file path, then what it does), an arrow is an import. Agents read and write that file as it is; `archdiff import note.md` takes any document that holds such a flowchart (a design note, an ISD, another tool's export) as the contract; `archdiff intent --init` seeds one from the code of a repository that has code and no contract yet.

The **intent** view draws the contract against the code: planned and not built yet dashed blue, built plain, the code's modules and imports beyond the contract orange. Draw on it in `✎ edit` and press **code this** in the Chat tab: the drawing goes into `ARCHITECTURE.md` first (so it is the contract before it is code), then the agent builds what the contract names and the code lacks. **improve the diagram** has the agent review the contract — names, missing links, layers, what the prose leaves open — and edit the file; **from document** turns a pasted design note into it (a note that already holds a flowchart needs no agent). The agent may ask you a question with options (a fenced `archdiff-question` block in its answer): the Chat tab shows the options as buttons, and the answer resumes its session. `archdiff check` (exit 1 on an import between two of the contract's layers that no arrow of the contract allows, or on a violation of a rule `archdiff.json` states beside it: [Rules beside the layers](#rules-beside-the-layers)) keeps the code to it in CI; it also lists what is planned and not built and what was built beyond the contract.

**An old repository adopts the contract with a baseline.** `archdiff check --baseline` writes the violations the code has now to `archdiff-baseline.json` — at the root, beside `archdiff.json` and `ARCHITECTURE.md`, to be committed and read in the same review as the contract it excuses, and not under `.archdiff/`, which holds the cache and is ignored; `"baseline"` in `archdiff.json` (or `--baseline FILE`) names another path. From then on `check` exits 1 only on a violation that is not in the file: it lists the known ones apart with their count, and names the entries that no longer occur, so the file shrinks as the code is fixed (`--baseline` writes it anew; a line can be removed by hand as well). A violation is known by what it is — the rule, the importing module, the imported one — not by its line, so an edit above an import does not make it new. `--no-baseline` holds the code to none, to see the whole debt; `--json` gives every violation with `"known"`, the entries that no longer occur as `"stale"`, and `"ok"`, which is the exit code. The page's check and the checks after an agent's run hold the code to the same baseline, and `--baseline` never writes over a file that is not archdiff's.

## From a drawing to code: the Chat tab

Draw the change on a view in `✎ edit`: a shape with a name is a new module (`src/lib/refunds.ts`) or a new function (`refund`, placed in the nearest module, or `path#name`), an arrow between shapes is an import or a call, a deleted shape is a removal, free text is a note. Save, open **Chat**, and *read the task*: archdiff diffs the drawing against the code graph and writes a Markdown task with the files and lines it touches, the layers it crosses (a new dependency between layers is flagged) and the rules to keep. Edit the task, then *run* it: the agent runs in this repository and its output streams into the tab; a follow-up message continues the same session. When it finishes the diagram reloads, and `review` shows what the agent changed against what was drawn.

The agent is picked at the top of the Chat tab, among those installed on this computer: Claude Code (`claude -p … --permission-mode acceptEdits`), Cursor (`cursor-agent -p --trust …`), Codex (`codex exec --json` in its workspace-write sandbox) and OpenCode (`opencode run --format json --auto`); the page remembers the pick, and a follow-up goes on with the agent that holds the session. `archdiff web --agent codex` (or `"agent"` in `archdiff.json`) is the one picked first, else the first installed; `"agent"` may also be `{ "command": ["…"], "resume": "--resume", "protocol": "stream-json" }` for another CLI that prints Claude's stream-json (or `"codex"`, `"opencode"`: their events). With "none" picked, or none installed, the tab only writes the task (`archdiff plan` does the same from the terminal). Nothing runs by itself: every run starts from the button with the prompt as shown, every prompt is kept in `.archdiff/tasks/`, one run goes at a time, and the server refuses a request from a page of another site.

**The settings** — the ⚙ of the header, or *agents & keys…* beside the picker — are yours and no repository's: `~/.archdiff/settings.json`, written for you alone, never `archdiff.json`, so a key cannot land in a commit. They hold the language of the page too (`"language": "uk"`; English needs no entry). An agent is looked for by its name on the PATH and then where its installer puts it for you (`~/.local/bin`, `~/.opencode/bin`, npm's directory on Windows; a server started from a desktop application often has a PATH without them), and the window shows the program started for each, or why none is. Place a program by its path when it is elsewhere, name the model an agent is told to use (`--model` for Claude Code and Cursor, `-m` for OpenCode, the `model` configuration value for Codex), and add agents of your own: a command, the events it prints, its resume flag. Every change is kept at once. On Windows a command npm installed is a batch file (`codex.cmd`), which Node does not start and which could take no task of several lines: archdiff reads it for the script or the program it runs and starts that, the task one argument as it was written; a stopped run ends the processes its agent started. A key is an environment variable named `…_KEY` or `…_TOKEN` (`OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `CURSOR_API_KEY`…): every agent run gets the keys set there over the environment archdiff was started in; the page is sent only that a key is set and its last four characters, and a key an agent prints is blotted out of the transcript. **OpenRouter**: set `OPENROUTER_API_KEY` and give OpenCode a model `openrouter/<model>`, or tick *through OpenRouter* for Claude Code, which then runs on that key (`ANTHROPIC_BASE_URL=https://openrouter.ai/api`, the key as `ANTHROPIC_AUTH_TOKEN`, Anthropic's own key emptied, as OpenRouter documents it). The settings are read and changed from the computer archdiff runs on and no other, however the server is bound.

## Asked by the agent: the MCP server

`archdiff mcp` serves the same analysis to a coding agent while it works, over the [Model Context Protocol](https://modelcontextprotocol.io) on stdin and stdout: the agent asks a question when it has one, instead of getting pictures in its prompt.

| Tool | Arguments | What it answers |
| --- | --- | --- |
| `views` | `kind`, `changed`, `base`, `head` | The list `archdiff views` prints, `key<TAB>title` per line; `kind` keeps one kind (`module`, `calls`…), `changed` the views of the files changed since the base |
| `diagram` | `view`, the picture options (`depth`, `limit`, `weight`, `hubs`, `packages`, `expand`, `hide`, `overlay`, `changes`, `only`, `changed`, `mermaid`, `lanes`, `types`), `base`, `head`, `heads` | One view by its key (`layers`, `module:src/x.ts`, `calls:src/x.ts#fn`, `cycles`…) as Markdown with Mermaid, as `archdiff diagram` writes it; the options are the one table, by the names the API's query gives them |
| `check` | none | What `archdiff check` reports: the imports against the contract and what breaks a rule of `archdiff.json`, with their files and lines (the ones the baseline lists apart), what is planned and not built, what is built beyond it |
| `may_import` | `from`, `to` | Whether the contract lets one module import another, asked before the import is written. Each end is a path (a file still to be written is placed by its path) or a layer's name. *Allowed* (one layer, or an arrow of the contract across the two, which is named), *Not allowed* (with the layers the importer may use), or *Not judged* (a layer the contract does not name, or no contract) |
| `impact` | `target`, `depth` | What `archdiff impact` reports of a module (`src/db/store.ts`) or a function (`src/db/store.ts#saveOrder`): the risk of a change with the parts of its score; who depends on it — the modules that import it or call into it, or the functions that call it, and who imports and calls those, up to `depth` steps away (3 unless said) — each with what it reaches the target through and the file and line that is written at; and every test that reaches it, however far, with the test files that only import its module named apart — the tests to run after the change |
| `review` | `base`, `head` | The architectural diff of the working tree (or a head) against a base, as `archdiff review` writes it: what was added, removed and changed, and the new dependencies between layers, marked when the contract forbids them |

| `search_code` | `pattern` | Every line of the analysed source files that has the text (a capital makes the case count) or matches the regular expression written between slashes, with its file and line; at most 200 lines, the rest counted |
| `search_diff` | `pattern`, `base`, `head` | Every line the change added (+) or removed (−) that has it: the working tree (or a head) against the base, the working tree's untracked files included |

Every answer is of the code as it is now: a call reads the analysis again (the fact cache keeps that fast), so the agent's own edits are in its next answer. The tools only read — none changes the code, the contract or a drawing. A wrong call is a JSON-RPC error (`-32602`) carrying the message the CLI gives for the same mistake (`diagram: unknown view "nope"`, `diagram: no module "src/none.ts" (archdiff views lists them)`); a tool that ran and failed (a review outside git) answers with the reason, marked `isError`.

The page's Chat tab hands the server to Claude Code by itself with every run (`--mcp-config`, with its tools allowed), so nothing is to be set up for it there. For Claude Code in a terminal, and for the other agents, register it once with the agent, which then starts the server itself:


or in the agent's own file — Claude Code's `.mcp.json` at the root of the repository, Codex's `~/.codex/config.toml` (or `.codex/config.toml` of a trusted project), OpenCode's `opencode.json`:

```json

```

```toml

command = "npx"
args = ["-y", "@ivlad003/archdiff", "mcp"]
```

```json

```

An OpenCode from before the `servers` key takes the same entry directly under `"mcp"`. With archdiff installed (`npm i -g @ivlad003/archdiff`) the command is `archdiff mcp`, which starts faster than `npx`. The server reads the directory it is started in, which these agents make the repository; `archdiff mcp path/to/repo` names another.

The protocol is written by hand — no SDK, the package keeps its two runtime dependencies: JSON-RPC 2.0, one message per line, `initialize`, `ping`, `tools/list` and `tools/call`, no HTTP transport. It speaks the revisions that open with the `initialize` handshake (2024-11-05 to 2025-11-25); a client of the 2026-07-28 revision, which has no handshake, probes with `server/discover`, is told the method is not found, and falls back to the handshake as that revision prescribes.

## Layers

Without configuration a module's layer is its top directory, or `src/<dir>` under `src/`. `archdiff.json` at the root names them explicitly:

```json
{
  "layers": { "routes": ["src/routes/**"], "lib": ["src/lib/**"], "db": ["src/db/**"] },
  "other": "shared",
  "exclude": ["**/*.stories.tsx"],
  "entries": ["src/jobs/**"],
  "hubs": { "min": 6, "share": 0.25, "max": 40 },
  "storages": { "src/cache/**": "the cache" },
  "storagePackages": { "my-orm": "MyORM" },
  "checks": ["npm test", "npm run typecheck"],
  "tours": "docs/tours"
}
```

Without `layers`, a repository with an `ARCHITECTURE.md` takes the contract's layers. A file no layer's globs match falls in the layer `other` names (`other` by default). `entries` adds entry points the analysis cannot see (a job runner's files); `postman` names Postman collections to read against the code besides the ones named like an export; `tours` names the directory the guided tours are kept in, one the repository commits (`.archdiff/tours` without it); `hubs` sets when a module is a hub (a badge, not lines); `storages` and `storagePackages` name stores the code's names, packages and calls (the file system, `fetch`, a database client's `query`, Python's `open`, Rust's `std::fs`, PHP's `PDO`) do not reveal; `checks` are the commands run after every agent run; `baseline` names the file of the known violations (`archdiff-baseline.json` without it); `rules` are the next section's. archdiff keeps itself in the same contract: its own `archdiff.json` and `ARCHITECTURE.md` are in the repository and `archdiff check` is green on it.

A file a module names by a URL — `new Worker(new URL("./worker.ts", import.meta.url))`, a child process given `fileURLToPath(new URL(…))`, a hook `module.register` loads — is a dependency too, drawn as a dashed line labelled `loads`, and the module's page says *loaded by URL*. Imports resolve per language: TypeScript/JavaScript like the compiler (relative paths with or without extensions, `.js` written for a `.ts` file, `index` files, the `paths`, `baseUrl` and `rootDirs` of the nearest `tsconfig.json`, `extends` into node_modules; a file on disk that is no module — a JSON, a stylesheet, an image, `public/` behind an absolute path, a source under a hidden directory — is an asset, nothing missing), Python by dotted path from the repository root or `src/` (the standard library known by name), Rust by `crate::`/`self::`/`super::` paths over the targets of each `Cargo.toml` (workspace members and dependencies known; `tests/`, `benches/` and `examples/` files are crates of their own), PHP by qualified name against the declarations of the repository and the namespaces of the composer lock, Go by import path over the `go.mod` files (a package is its directory: each declaration used is found in the file of the package that declares it; a path of no module of the repository is the standard library or a package), Java by qualified name against the classes the repository declares, whatever the source root (a class used without an import is looked for in the file's own package, then in the packages imported with `.*`; `java.` and `javax.` are the JDK, any other package an external named by its first three elements), C# by qualified name against the classes the repository declares (a class named without its namespace is looked for in the namespaces around the file's own, in those it uses, then in those a `global using` of the repository names; `System` is .NET, any other namespace a package, named as a `PackageReference` of the nearest `.csproj` names it). Everything else is a package or a built-in. One repository may mix them; the layers and the diagrams are the same.

A call out of the repository that names an operation of an API archdiff knows is not a blind spot. SCAPI, the Salesforce Commerce API as the storefront-next runtime and commerce-sdk-isomorphic expose it, is known: `clients.shopperBaskets.getBasket()`, a destructured `shopperProducts.getProducts()`, a client typed `ShopperOrders` — the operation `ShopperBaskets.getBasket` is a shape of its own on a call tree, a message to the family's lifeline in a sequence, a storage the path and the flow end at, the reason `api` in the coverage report, and the `apis` view counts them by family and module. The OCAPI hooks a cartridge declares in `hooks.json` (`dw.ocapi.shop.basket.modifyGETResponse`, whose entry is the export the name ends with) are joined to the family serving the resource they modify. The contract of an operation as the code uses it — what the call sites send, key by key, and what the code reads of the result (`const { data } = await op(); data.productItems`, also through a function that returns the result, four calls deep, and through the callback an array of it is iterated with) — is on the operation's page, under an `apis` picture, in `archdiff apis` and in the Postman collection `archdiff postman` writes.

## Rules beside the layers

The flowchart of `ARCHITECTURE.md` says which layer may import which. What it has no room for, `"rules"` in `archdiff.json` states, and `archdiff check` holds the code to them as it does to the arrows, with or without an `ARCHITECTURE.md`:

```json
{
  "rules": [
    { "kind": "naming", "layer": "services", "pattern": "*.service.ts" },
    { "kind": "threshold", "metric": "instability", "max": 0.5, "layer": "domain" },
    { "kind": "threshold", "name": "no huge file", "metric": "lines", "max": 600 },
    { "kind": "cycles" },
    { "kind": "through", "from": "routes", "to": "db", "through": "src/db/index.ts" },
    { "kind": "forbidden", "from": "domain", "imports": ["node:fs", "express", "src/routes/**"] }
  ]
}
```

| Kind | What it asks | Fields |
| --- | --- | --- |
| `naming` | The files of `layer` are named by `pattern` — a glob of the file's name, or of its path when it has a slash — or by `regex`, a regular expression of the name | `layer`, and `pattern` or `regex` |
| `threshold` | A number of every module (of `layer`, when given) stays at or under `max` and at or over `min`: `fanIn` (Ca), `fanOut` (Ce), `instability`, `abstractness`, `distance` (from the main sequence), `cohesion`, `lines`, as `archdiff metrics` measures them | `metric`, `max` or `min` or both, `layer` |
| `cycles` | No more than `max` import cycles (none, without it); with more, every import inside a cycle is a violation, so a cycle is fixed at an import and a known one stays the same violation while the cycle shrinks | `max` |
| `through` | The modules of layer `from` (of every other layer, without it) reach layer `to` only through the module `through` names — a path, a glob, or a list: a facade inside the layer, or a gateway before it | `to`, `through`, `from` |
| `forbidden` | The modules of layer `from` (every module, without it) import none of `imports`: a module's path, a glob, a package or a built-in by its ID (`pkg:express`, `node:fs`) or by its name | `imports`, `from` |

Every violation is reported as an import against the layers is, with its file and line — `` `src/routes/peek.ts:1` imports `src/db/store.ts`: layer **routes** reaches **db** only through `src/db/index.ts` (rule `through:routes→db`) `` — a module's own name or number at its line 1; it fails `check` (exit 1), is in `--json` with its `rule`, and can be known to the baseline. A rule's `name` is how the report and the baseline know it; without one it is the rule's kind and what it is of (`naming:services`, `instability:domain`, `lines`, `cycles`, `through:routes→db`, `forbidden:domain`), and two rules of one name are refused. A type-only import breaks no rule, as it crosses no layer: nothing of it runs. A rule written wrong names its field (`archdiff.json: "rules[1].metric" must be one of fanIn, fanOut, …`), a field its kind does not take is refused — a misspelt one would loosen the rule unseen — and a rule of a layer the repository does not have is a wrong call of `check` (exit 2, with the layers there are), not a rule that silently holds. archdiff states two of its own: no import cycle, and views that import nothing of Node.

## Languages

What archdiff reads of each language, and what it does not. A call it does not follow is a gap with its reason, never a guessed line; `archdiff coverage` counts them.

| Language | Imports resolve | Calls followed | Not followed |
| --- | --- | --- | --- |
| TypeScript, JavaScript | as the compiler resolves them: relative paths, `index` files, `.js` written for `.ts`, tsconfig `paths`, `baseUrl` and `rootDirs`, workspace packages, CommonJS `require` | declarations, import bindings (re-exports, namespaces), `this.m`, `super.m`, a member of a value whose class the code writes or a call's declared result gives, an interface's implementers | a computed callee, a value whose class the code does not write, an object literal's functions |
| Python | dotted paths from the root, `src/` or a project directory; relative imports; what a package's `__init__.py` re-exports; the standard library by name | `def`s, `self.m`, `super().m`, a member of an annotated parameter or local, of `x = Repo()`, of an attribute the class's methods fill with one class, of a call's `-> Repo` | `getattr`, dynamic imports, a value no annotation types; a decorator that may replace a function is noted |
| Rust | `use` paths (`crate::`, `self::`, `super::`, workspace members, `path` dependencies) over the targets of each `Cargo.toml` | path calls, `Self::f`, `self.m`, a method of a parameter typed `&Order` or of a struct's field; `#[test]` and `#[cfg(test)]` items are left out | trait objects and generics, macros (not expanded), inline modules, an `impl` for a type of another file; no `logic` flowchart |
| PHP | qualified names against the declarations of the repository and the namespaces of the composer lock; `include` of a file | `$this->m()`, `self::`, `parent::`, a member of a typed property, parameter or promoted constructor parameter (a docblock's type too), traits, an interface's implementers | `$obj->$m()`, magic methods (`__call`, `__get`); no `logic` flowchart |
| Go | import paths over the `go.mod` files of the repository (`replace` to a directory too); a package is its directory, so each `pkg.Name` is found in the file of the package that declares `Name`, and a name used without a package in another file of the same directory; the standard library and the packages a `go.mod` requires are externals | functions of the package and of imported packages, `s.m()` on the receiver, a method of a parameter, a `var`, a literal (`&Order{}`, `new(Order)`), a type assertion or a field of the receiver's struct, of what the call that made a local returns (`repo := store.NewRepo()`), of a package variable; a method written in another file than its type; an embedded struct's methods; a function handed over (`http.HandleFunc("/", h.Place)`) is a dashed line | a call through an interface (which types satisfy it is not computed) or a type parameter, a function value, the variable of a `range` or of a type switch, a field of a struct declared in another file, reflection, cgo, a dot import; a package named otherwise than its directory |
| Java | qualified names against the classes the repository declares (nested ones too), whatever the source root; a class used without an import is one of the file's own package, then of a package imported with `.*`; a static import is its class; the JDK (`java.`, `javax.`) is the language's, any other package an external named by its first three elements (`org.springframework.web`) | a method of the class, of a class around it or of a static import; `this.m()`, `super.m()`, `super(…)`; a method of a field, a parameter or a local declared with a class or made with `new` (a `var` made by a call: what the call's target returns), of a cast, of a class named for a static method; through an interface or an abstract class, the classes implementing it; `new Order()` is a line to the class; a record's accessors; a method reference handed over (`this::audit`) is a dashed line | a lambda's parameter, a generic's element (`list.get(0).m()`), an inherited field, a class written as `Outer.Inner`, reflection, what an annotation processor generates (Lombok's getters, MapStruct); annotations are not read, so a framework's entry is known by its module's name only (`…Controller`, `…Handler`, `…Listener`) |
| C# | qualified names against the classes the repository declares (nested ones too): a `using` names a namespace and no file, so a class named in a type or called on is looked for in the namespaces around the file's own, outermost last, in each namespace it uses, then in those the repository's `global using` directives name; an alias and `using static` are their class; `System` and what is under it is .NET (`dotnet:System.Linq`), any other namespace a package named by the `PackageReference` of the nearest `.csproj` it starts with, else by its first two elements | a method of the class, of a class around it or of a `using static` class; `this.M()`, `base.M()`, `: base(…)`; a method of a field, a property, a parameter (a lambda's typed one too) or a local declared with a class or made with `new`, of `var x = call()` and `var x = await call()` by what the call's target returns (a `Task<T>` once awaited), of a cast and `x as T`, of `x?.M()`, of a class named for a static method; through an interface, the classes implementing it; a `partial` class is one class across its files; top-level statements are the program's `Main`; a method group handed over (`app.MapGet("/", Handlers.Get)`) is a dashed line | an extension method (`order.Shout()` is a member the class lacks), the variable of a `foreach` over an untyped collection, a generic's element, a field or a property declared in another part of a `partial` class, `dynamic`, reflection, what a source generator writes; a method a class with a base does not declare is read as inherited, not as a `using static` one; attributes are not read, so a framework's entry is known by its module's name only (`…Controller`, `…Handler`) |

## What the diagrams cannot show

A call is followed when its callee is a declaration of the same file, an import of a repository file (re-exports, a namespace, a glob, a `require` or an `import()` in a function), a member of a class the file declares or imports (its bases and PHP traits too), `this.m` inside a class, or a method of a value whose class the code names: a parameter, a local, a field or a constant typed with it or made with `new`, or the result of a call whose target declares it (`const s = makeStore()`, `await load()` of a `Promise<Store>`). Through an interface it reaches every class implementing it. Everything else is a gap with a reason: `dynamic` (a computed callee, or a call through a parameter), `unknown-member` (a known class without that member) `interface` (an interface no class implements: an object literal's function, a value injected from outside) and `unresolved` (a name an import binds that resolves to no file) are blind spots inside the repository; `member-of-value` (`list.map`, `req.on`, `expect(x).toBe`, a constant `new Map()`), `global` and `external` (a package, a built-in, the `resolve` of a `new Promise`) are calls out of it; `local` is a call of a function of the caller's own body (a nested function, a local arrow), whose calls are the caller's already. A parameter or a local spelled like a function of the module is never taken for it. `archdiff coverage` and the Coverage tab of the page list them by module, with the constructs read but not followed (an `eval`, a computed import), so an empty diagram is never read as proof.

## Which Mermaid type where

Every view exports as a Mermaid flowchart; some views read better as another Mermaid type, chosen with `--mermaid` (or the export menu on the page). `--mermaid flowchart` draws any picture as a flowchart (a sequence as its modules and numbered messages); a type that does not fit the view — a gitGraph off the timeline and the branches, a state diagram of no machine, a quadrant off the hotspots and the metrics — is not drawn empty: the picture keeps its own type, with a comment saying why. A marked line (added, removed, changed) keeps its colour in a flowchart (`linkStyle`), and a folded shape's Markdown lists every shape it stands for.

| View | Mermaid type | Why |
| --- | --- | --- |
| `sequence:` | `sequenceDiagram` (automatic) | the order of calls across modules; `calls:` is the same calls as a tree, a flowchart |
| `classes` | `classDiagram` (automatic) | fields, methods, inheritance in UML's own notation |
| `layers`, `packages` | `C4Context` (`--mermaid c4`) | boundaries and containers, the architect's vocabulary |
| `hotspots` | `quadrantChart` (`--mermaid quadrant`) | size against calls in, the big and central modules top right |
| `layers`, any lanes | `pie` (`--mermaid pie`) | the share of modules per layer |
| `timeline` | `gitGraph` (automatic) | commits in order, tagged where a coupling appeared |
| `branches` | `gitGraph` (automatic) | each branch opened where it left the base or the branch it was started on |
| `dir:`, `layer:` | `mindmap` (`--mermaid mindmap`) | a tree of what lives where |
| `matrix`, `metrics` | a Markdown table (`metrics` also a `quadrantChart`) | a matrix is a table; I against A is a quadrant |
| `machine:` | `stateDiagram-v2` (automatic) | states and transitions in their own notation |
| `logic:` | `flowchart TB` with diamonds (automatic) | a function's branches top down, the way a flowchart is read |

Not used, and why: an ER diagram needs a schema (a later step with Prisma or SQL files); Gantt, Kanban, journey, Sankey, XY and the rest describe work or data, not code.

## Exports

Every view (and the review) exports to draw.io / diagrams.net (`.drawio`, uncompressed, each cell carrying the archdiff ID and the code position), Excalidraw (`.excalidraw`, shapes with bound text and arrows), Archi (ArchiMate Open Exchange XML: components, functions, relationships and one view at the laid-out places) and Mermaid.

## Speed, cache and CI

Facts are cached by file content in `.archdiff/facts.json.gz` (add `.archdiff/` to `.gitignore`), under a version that is a hash of the extractors' own sources, so a changed extractor empties it by itself; a second run parses only what changed. The files of other revisions — a review's base, a history's commits, a comparison's heads — are cached apart, in `.archdiff/revisions.json.gz` (the 4000 most recently read versions), so a second `history` reads git and nothing more. Symbolic links inside the repository are read once, under their own path, when git does not list the files. Cold start parses in worker threads: about 6 s for 500 files, 9 s for 2300. In CI, persist `.archdiff/` between runs and fetch enough history for the merge-base (`fetch-depth: 0`), or pass `--base origin/main`; `archdiff check` fails the job on a violation of the contract that the committed baseline does not list (it needs no history), and [docs/ci.md](docs/ci.md) has the lines. Files over 1.5 MB are skipped and listed by `coverage`. Directories whose name starts with a dot (`.git`, `.claude`, `.agents`) are not analysed, nor `node_modules`, `dist`, `build`, `coverage`, `out`, `.next` and `.cache`; `"exclude"` in archdiff.json leaves out more. `--out` only writes a new file or one archdiff wrote before. `web` binds to localhost and refuses requests whose Host header is not its own; `--host 0.0.0.0` exposes the sources to the network. The analysis of what can go wrong on real repositories is in [docs/production.md](docs/production.md); the test pass over eight kinds of user and four real repositories (requests, ripgrep, Slim, express) is in [docs/qa-2026-10-16.md](docs/qa-2026-10-16.md).

## Specification

The **Spec** tab of the page lists the specification and has the agent write it: *spec this view* writes the OpenSpec spec and the Gherkin feature of the view's subject (a layer, a directory, a module; every layer from an overview), *review all specs* checks every spec against the code, *validate* runs the OpenSpec CLI; the task goes through the Chat tab like any other, and the agent asks when a behaviour is a real choice. In the terminal, `archdiff spec` lists them, `archdiff spec --prompt <view>|all|update` prints the task (pipe it to any agent), `archdiff spec --validate` validates, and `archdiff spec --tests` writes a test skeleton per Gherkin scenario (`tests/<feature>.test.ts`, each test marked to do with its steps as comments; a file archdiff did not write is kept), so a scenario without a test is visible. The **copy** button beside the tabs copies what the active tab shows: the Markdown, the file, the coverage, the flow, the transcript or the spec.

The behaviour is specified twice, for tools and for people: `openspec/specs/<capability>/spec.md` in the [OpenSpec](https://github.com/Fission-AI/OpenSpec) format (requirements with SHALL, scenarios with WHEN and THEN; `npx @fission-ai/openspec validate --specs` checks them, `openspec view` browses them) and `features/*.feature` in Gherkin (the scenarios the end-to-end tests run, readable by Cucumber and IDE plugins). `openspec/project.md` holds the context: the stack, the pipelines, the conventions. When a behaviour changes, its requirement and its scenario change with it.

## Development

```bash
npm install
npm run typecheck
npm test          # the CLI, the HTTP API and the MCP server, through the real binary
npm run test:web  # the page in headless Chrome (playwright-core; skipped without Chrome)
node bin/archdiff.js web .
```

`npm pack` compiles `src/` to `dist/`, copies the tree-sitter grammars to `dist/wasm` and bundles the page (Excalidraw, React, marked) to `dist/web`, about 6 MB with the fonts. The published package has two runtime dependencies, `web-tree-sitter` (the parser, WebAssembly) and `smol-toml` (the `Cargo.toml` files of a Rust repository); no native code is compiled on install.

The VS Code extension is a package of its own, outside the npm package: `cd vscode && npm install`, then `npm run typecheck`, `npm test` (node's test runner; its parts run against the archdiff of this checkout, and the panel's document in Chrome), `npm run test:editor` (the extension inside a real VS Code, on a stand-in archdiff) and `npx @vscode/vsce package` for the `.vsix`.
